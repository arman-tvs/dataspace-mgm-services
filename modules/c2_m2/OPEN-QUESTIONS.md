# C2-M2 Users and App Access: open questions

Points where the spec (`spec/C2-M2-AppAccess`, version 0.2) is unclear or where this implementation had to choose a reading.

| No. | Question | Spec | Reading implemented | Who decides |
|---|---|---|---|---|
| 1 | Own database `c2_m2` in PostgreSQL (`DATABASE_URL`). | README 4, 5 | With `DATABASE_URL` set: PostgreSQL through SQLAlchemy (MIT, connection pool) with the driver `pg8000` (BSD-3-Clause); the schema is versioned with Alembic (MIT, `c2_m2_impl/dao/jdbc/migrations/`, version table `alembic_version_c2_m2`) and upgraded to `head` at start; the services reach the database only through `DaoService` (`ctx.dao`): it holds every DAO, and `ctx.dao.lock(...)` takes the locks of 6.14 in their fixed order through the DAOs (`templates.lock`, `companies.lock`, `invitations.lock_staff`/`lock`, `company_users.lock_account`) as transaction-scoped advisory locks (`pg_advisory_xact_lock`) inside one SQLAlchemy session transaction, released by PostgreSQL at commit/rollback. Domain errors commit what was saved before them (for example the failed name check of 7.10); other errors roll back. Without `DATABASE_URL` the module does not start (no in-memory tables); the C2-M2 tests and `demo.py` need a PostgreSQL. `sqlalchemy`, `alembic` and `pg8000` are in `pyproject.toml` and `uv.lock`. Open: `DEPENDENCIES` is not yet regenerated (Eclipse Dash check). `reset()` does not truncate the database; `tests/c2_m2/conftest.py` empties the tables before each test when `DATABASE_URL` is set. Run against PostgreSQL 16 with Keycloak: C2-M2 tests and `demo.py` scenarios 1 to 3 pass. | Team, spec authors |
| 2 | `SUBSCRIPTION_URL` and `COMPANY_URL` name the neighbour addresses. | README 4, 11.2 | The module does not read them (AGENTS.md rule 6); `portal_common.neighbours` resolves `C10_M1_URL`, `C3_M1_URL` and `MODULE_URLS`. Empty address = built-in stand-in. | Scaffold |
| 3 | Files of the built-in stand-ins have no configuration variable in section 4 (C1-M3 has `STUB_*_FILE`). | README 11.2, 14.2 | Fixed files `stub-subscriptions.json` and `stub-companies.json` in the module folder, with the test values of 14.2. | Spec authors |
| 4 | 7.16 requires a binding to the OSP company before direct staff roles; 6.7 limit 4 also allows accounts without a company. | README 6.7, 7.16 | 7.16 as written: without a staff role yet, only accounts bound to `ospCompanyId`; others are invited (7.17). | Spec authors |
| 5 | Without `IAM_URL` there is no Admin API. | README 11.1, 14.1 | The module always calls Keycloak (`KeycloakPortalIam`) and assumes `IAM_URL` points at a reachable Admin API; there is no in-memory stand-in. Without `IAM_URL` every call of 11.1 fails as an IAM error. | Team |
| 6 | Errors of a neighbour: README 11.2 says 502 `upstream-error`; the shared rule gives 502 `neighbour-rejected` for a 4xx answer. | README 11.2, 12 | Shared rule of `portal_common.neighbours`; a 404 of C3-M1 counts as "company not active". | Scaffold, spec authors |
| 7 | `assign-company-admin` on a binding `DISABLED`: which event? | README 8.8 step 5 | `UserAssignedToCompany` with `via` `ONBOARDING` and the restored portal roles; on a binding `ACTIVE` only `UserRolesChanged` if `Company Admin` was added. | Spec authors |
| 8 | 9.1 `templateExists` for a template whose creation was interrupted (row without `iam_client_uuid`). | README 9.1 | `false`, as for an app without a template. | Spec authors |
| 9 | 7.12 `portalRoles` and `staffRoles`. | README 7.12 | `portalRoles` = company portal roles only, `staffRoles` = staff roles; `Applicant` in neither. | Spec authors |
| 10 | 7.5: which instance clients count as target clients of a single-instance app. | README 6.10 | The one `SINGLE` client with status `ACTIVE`, if the company has any active subscription to the app. | Spec authors |
| 11 | Events of C2-M2 run as a service of its own (`c2_m2_rs_service/main.py`, FRAMEWORK 4.7). FRAMEWORK 6 says a split-out module delivers its CloudEvents to `POST /api/v1/events/inbox` of the installation with the token of `svc-c2-m2`, but section 4 of the README names no variable for the address of that inbox, and `portal_common.events` has no forwarding. | FRAMEWORK 4.7, 6; README 4, 10 | The standalone service publishes into its own in-process relay only; nothing leaves the process. Inside the installation (scaffold) events flow as before. A configuration variable and forwarding belong in `portal_common` and the spec, not in this module. | Spec authors, scaffold |
